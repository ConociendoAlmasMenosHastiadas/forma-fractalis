**Priority**: High  
**Status**: ✅ Complete
**Reference**: https://paulbourke.net/fractals/tetration/

**Formula**: z_{n+1} = c^{z_n}
- **Name**: Tetration (confirmed)
- **Initial iteration**: z₀ = c, then iterate z₁ = c^c, z₂ = c^(c^c), etc.
- **Complex exponentiation**: Use principal branch (already used in other fractals)
- **Escape test**: When a quality of z_n surpasses a threshold, return n
- **Default threshold**: 1e7 (1 × 10⁷)

**Escape Criteria System** (expandable parameter system):
All four options available as radio buttons:
- Magnitude exceeds threshold (default)
- Real component exceeds threshold
- Imaginary component exceeds threshold  
- Either real or imaginary exceeds threshold

## Recolor Feature (Iteration Cache)
**Priority**: High
**Status**: ✅ Complete (Mandatory as of final implementation)

**Description**: Cache iteration data to enable instant recoloring without re-computing fractals. This dramatically speeds up color experimentation and is now a core part of the rendering architecture.

**Key Decision**: After testing, the cache was made mandatory rather than optional. The memory overhead (~4.5 MB for preview) is negligible on modern systems, and the UX improvement is significant.

**Implementation Breakdown:**

**Phase 1: Cache Architecture**
- [x] Design iteration cache structure (`IterationCache` struct in app_state.rs)
- [x] Added to ViewState as `Option<IterationCache>`
- [x] Defined cache invalidation rules (view, fractal type, parameters, dimensions, max_iter)
- [x] Implemented `is_valid()` method for cache validation

**Phase 2: Core Caching Logic**
- [x] Created `compute_iterations()` function to compute without coloring
- [x] Created `apply_colors_from_cache()` to apply colors to cached data
- [x] Modified `render_fractal()` to always use cache
- [x] Automatic cache storage after every computation
- [x] Automatic cache invalidation when parameters change
- [x] Removed legacy non-cached rendering path

**Phase 3: Simplified to Mandatory Cache**
- [x] Removed `cache_enabled` toggle (cache is always active)
- [x] Removed Performance section GUI controls
- [x] Simplified rendering logic (removed conditional branches)
- [x] Code cleanup: removed ~47 lines of conditional logic

**Performance Insights:**
- Iteration computation is parallelized (Rayon)
- Color application is parallelized separately
- Cache uses u32 per pixel (4 bytes): 1380×820 = ~4.5 MB, 4K = 33 MB
- Instant recoloring when cache is valid (colors only take ~10-20ms)
- Log messages with `[CACHE]` prefix for debugging (use `--profiling` flag)

**Architecture:**
- Cache is transparent - users never interact with it
- Automatically invalidates on view/zoom/iteration/parameter changes
- Always populated after every fractal computation
- Single code path: check cache validity → use or compute+cache → apply colors

**Phase 4: Testing & Polish**
- [x] Test cache invalidation scenarios
- [x] Verify memory usage matches predictions
- [x] Test with all fractal types
- [x] Performance benchmarking

**Test Results:**
- Cache properly invalidates on zoom, pan, iteration changes  
- Instant recoloring confirmed when changing colormap/period/log scale
- Cache is transparent and automatic - no user intervention needed
- Performance improvement significant and consistent across all fractals
- With `--profiling` flag: `[CACHE]` messages confirm cache behavior

**Memory Allocation (always allocated):**
- 1380×820 preview: ~4.5 MB (1,131,600 pixels × 4 bytes)
- 1920×1080: ~8.3 MB (2,073,600 pixels × 4 bytes)  
- 3840×2160 export: ~33 MB (8,294,400 pixels × 4 bytes)
- Negligible on systems with 4+ GB RAM (target audience)

**Benefits:**
- Instant color scheme switching (10-20ms vs seconds)
- Real-time period/log scale adjustment
- Encourages rapid color experimentation
- Professional workflow with zero configuration
- Simpler codebase (~47 lines removed)
