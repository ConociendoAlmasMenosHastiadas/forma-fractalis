## Overview
Version 0.2.7 adds GPU support for the Tetration fractal and introduces the perturbation
theory rendering engine for deep zoom. Perturbation theory is the feature that addresses the
coordinate-precision wall in deep zoom: instead of computing every pixel at high precision,
a high-precision reference orbit is computed once and nearby pixels are approximated using
cheap f64 delta arithmetic. This can make very deep zooms practical, but only when a large
fraction of the frame remains close to one or more long-lived reference orbits.

## Perturbation Theory (Deep Zoom Renderer)

### Background
At zoom levels beyond ~1e13, f64 runs out of precision and hi-prec BigFloat rendering must be
used. Hi-prec is accurate but slow: every pixel requires BigFloat arithmetic. Perturbation
theory addresses the coordinate part of this problem:

- Compute one reference orbit at the zoom center using BigFloat (expensive, done once per frame)
- For each pixel, compute a delta z_n relative to the reference using f64 (cheap)
- The Mandelbrot delta recurrence: `dz_{n+1} = 2*r_n*dz_n + dz_n^2 + dc`
  where `r_n` is the reference orbit value at iteration n and `dc` is the pixel offset
- When `|dz_n + r_n|` escapes, record iteration count

Important clarification: PT is not a universal speedup for all deep or high-iteration views.
It works well when many pixels remain close to a long-lived reference orbit. When the chosen
reference escapes early or the frame contains many pixels whose orbits diverge quickly from the
reference, the renderer falls back to direct hi-prec work and the speedup largely disappears.

### What "Successful PT" Means for v0.2.7

The current implementation is best described as **basic PT plus tiled reference orbits**.
That is a solid foundation, but it is not yet the mature "deep zoom magic" stack used by the
fastest Mandelbrot renderers.

Useful taxonomy for this release:

- **Basic PT**: one hi-prec reference orbit, one f64 delta recurrence, direct fallback on glitch. This is implemented.
- **Tiled PT**: multiple reference orbits across the frame to reduce `|dc|` and extend the useful delta region. This is now implemented in the unified pipeline and in `pt_tiling_test.rs`.
- **Rebased PT**: when the current reference stops being representative, switch to a better tiled reference orbit before falling back per pixel. A bounded prototype is now implemented for Mandelbrot PT.
- **Series Approximation (SA)**: a conservative two-term Mandelbrot warm start is now implemented for the first `64` steps before the exact delta loop takes over. Broader skip tuning and benchmarking are still pending.

The practical implication: successful PT in v0.2.7 should mean "correct, user-visible, and materially faster on representative boundary / interior deep zooms." It does **not** mean "all deep views become fast." Exterior filament stress scenes should still be expected to have high fallback rates.

### Rebasing Design Pass (2026-05-06)

Goal: reduce expensive per-pixel hi-prec fallback on difficult views by switching to a better
reference orbit when the current one stops being representative, instead of immediately falling
back to direct rendering.

**Practical design for v0.2.x follow-up:**

- Reuse the existing tiled orbit infrastructure as the first rebasing candidate set. No new orbit family is needed for the initial design pass.
- Extend `pt_iterate` into a rebasing-aware variant that, on glitch or orbit exhaustion, returns the current iteration index and the current total orbit value `z_total = r_n + dz_n` instead of only `Err(())`.
- Candidate rebasing rule:
  - only consider candidate reference orbits that still have a valid orbit entry at the current iteration index
  - compute `dz_rebase = z_total - r_candidate[n]`
  - choose the candidate with the smallest `|dz_rebase|^2`
- Resume the delta recurrence from that iteration using the new `(reference orbit, dz_rebase)` pair.
- Apply a small per-pixel rebase budget (for example 2-4 rebase events). If all candidates are poor or the budget is exhausted, then fall back to direct hi-prec.

**Why this order is correct:**

- It uses data the renderer already computes (`compute_tile_orbits`) rather than introducing another expensive orbit-search system immediately.
- It targets the real current failure mode: too many pixels drop to fallback when one reference becomes locally poor.
- It can be validated against the existing scene matrix:
  - `scratch` should remain hard, but fallback rate should drop materially
  - `boundary` should show the clearest improvement
  - `period2` should not regress relative to the already-good 1x1 baseline

**Acceptance criteria for rebasing prototype:**

- No new correctness regressions in the agreement test
- Fallback rate decreases on `scratch` and `boundary` relative to non-rebased tiled PT
- Runtime improves on `boundary` without silently masking failures
- Profiling clearly reports rebase count, remaining fallback count, and whether rebase budget was exhausted

### Rebasing Prototype (implemented 2026-05-06)

- `pt_iterate` is now split into a resumable `pt_iterate_from(...)` plus a bounded `pt_iterate_rebased(...)` loop.
- On glitch or orbit exhaustion, the delta path now returns the current iteration index and `z_total = r_n + dz_n` instead of immediately falling back.
- Candidate rebase orbits are drawn from the already-computed tiled orbit set.
- The chosen candidate is the orbit with the smallest `|z_total - r_candidate[n]|^2` that also satisfies the same glitch threshold used for the active reference.
- Rebased segments resume with the candidate orbit's own `dc = c_pixel - c_ref`. This matters: rebasing is not just swapping the orbit pointer; the constant term must change with the new reference orbit.
- Rebase budget is currently fixed at `4` per pixel (`PT_REBASE_BUDGET`). If no viable candidate exists or the budget is exhausted, the pixel still falls back to the direct path.
- `PerturbationResult` now records `rebase_count`, `rebased_pixel_count`, and `rebase_exhausted_count` in addition to the final fallback count.

### Reference Orbit Module Design

The perturbation engine lives in `core/src/perturbation.rs` and is now reachable through
`RenderBackend::Perturbation`. Preview and export now both route through the unified core
rendering pipeline, so the old split-preview description is obsolete.

The API sketch below is historical background only. The current implementation has expanded
beyond it with `escaped`, tile-fraction fields, `render_perturbation_tiled`, rebasing, and
`PerturbationResult`.

The GUI-side `reference_orbits` cache is now legacy state. Active PT behavior is owned by the
core pipeline and `rendering_pipeline::latest_pt_report()`.

**Public API surface:**

```rust
/// A precomputed reference orbit. Immutable after construction.
pub struct ReferenceOrbit {
    /// r_n = (re, im) truncated from BigFloat to f64 after each iteration.
    /// Length equals the actual escape iteration of the reference point, or max_iter.
    pub orbit: Vec<(f64, f64)>,
    /// The zoom-center this orbit was computed for (used for cache validation).
    pub center_x: f64,
    pub center_y: f64,
    pub zoom: f64,
    pub max_iter: u32,
}

impl ReferenceOrbit {
    /// Compute the reference orbit for the Mandelbrot set (power=2) at the given center.
    /// `bits` is the BigFloat precision (128 minimum recommended).
    pub fn compute_mandelbrot(center_x: f64, center_y: f64, zoom: f64,
                              max_iter: u32, bits: u32) -> Self;

    /// Returns true if this orbit is still valid for the given rendering parameters.
    /// Any change to center, zoom, or max_iter invalidates it.
    pub fn is_valid_for(&self, center_x: f64, center_y: f64,
                        zoom: f64, max_iter: u32) -> bool;
}

/// Render one pixel using perturbation theory delta iteration.
/// Returns the escape iteration count.
pub fn pt_iterate(
    dc_re: f64, dc_im: f64,
    orbit: &ReferenceOrbit,
    escape_radius_sq: f64,
) -> u32;

/// Render an entire frame using PT. Returns iteration buffer (row-major).
pub fn render_perturbation(
    view: &FractalView,
    orbit: &ReferenceOrbit,
    fractal_params: &HashMap<String, f64>,
    max_iter: u32,
) -> Vec<u32>;
```

**Delta recurrence (Mandelbrot power=2):**
```
dz_0 = 0
dz_{n+1} = 2 * r_n * dz_n + dz_n^2 + dc
escape when |dz_n + r_n|^2 > escape_radius^2
glitch when |dz_n|^2 > glitch_tolerance * |dz_n + r_n|^2
```

**Coordinate mapping:**
`dc` = pixel offset from center in complex plane. Uses `screen_to_complex` formula but
computed as a delta, not an absolute position — this avoids f64 precision loss for the
center itself. `dc_re = (px - width/2) * (3.5 / zoom) * aspect / width` (same formula
as `screen_to_complex`, rewritten to subtract from center rather than add to an absolute).

**Cache invalidation in GUI state:**
The old single-orbit `ViewState` sketch is obsolete. Current PT GUI state keeps a tiled orbit
cache in `RenderState.reference_orbits`, plus `pt_tiles`, `last_orbit_view_w/h`, and `pt_bits`.
Changing backend away from PT, tile count, PT precision, or preview dimensions invalidates that cache.

### Glitch Handling

Current v0.2.7 behavior: when a pixel is detected as glitched, PT first tries bounded rebasing
within the already-computed tiled orbit set. Only after no viable candidate exists or the rebase
budget is exhausted does the pixel fall back to direct rendering.

- if `hiprec_bits > 64` and the fractal supports hi-prec, the final fallback uses `iterate_hiprec()`
- otherwise the final fallback uses direct f64 `iterate()`

This keeps failures explicit while still giving PT one more chance to stay on the delta path.

A glitch counter should be visible in the UI (e.g., "N glitched pixels (fallback used)").
This is information the user should see — it validates that PT is working and tells them
when the glitch fallback is expensive. Do not hide it.

### What this is NOT
- Auto-switching behavior (zero silent mode changes ever) — this is deferred to v0.3.6,
  where "Auto" is designed as a first-class mode with full visibility and explicit refusal
  semantics; by then the full pipeline family (GPU, CPU, PT, Hi-Prec, PT-GPU) will be in place
- GPU perturbation theory — see the full architectural analysis in the section below
- Perturbation theory for arbitrary powers (different recurrence; leave for a follow-up)
- An animation feature — just single-frame deep zoom rendering

### GPU Perturbation Theory: Architecture Analysis

This section answers the question: "Can perturbation theory benefit from GPU acceleration?"

**Short answer: Yes, the delta iteration is a perfect GPU workload. CPU-side reference orbit
computation is unchanged. The combination is called "Perturbation GPU" and is architecturally
feasible with clearly defined precision limits.**

#### Why GPU PT makes sense

The PT algorithm has two phases:
1. Reference orbit (BigFloat, runs on CPU, O(max_iter) — not parallelizable across pixels)
2. Delta iteration (f64 per pixel, O(pixels * max_iter) — embarrassingly parallel, ideal for GPU)

Phase 2 is identical in structure to escape-time GPU rendering except the per-iteration body
is the delta recurrence instead of `z = z^2 + c`. Each GPU thread handles one pixel, reads
from a shared read-only reference orbit buffer, and runs the recurrence.

At 4K (8M pixels) and 500k iterations, phase 2 requires ~4 × 10^12 f64 operations on CPU.
GPU PT would reduce this to seconds instead of minutes — the same speedup ratio as ordinary
GPU vs CPU rendering, but now unlocking that ratio for deep zoom.

#### GPU PT Architecture (for a future release)

The existing GPU composition architecture extends naturally:

**New binding layout (PT-specific common template `pt_common.wgsl`):**
```wgsl
struct PtParams {
    center_x: f32,
    center_y: f32,
    zoom: f32,
    max_iter: u32,
    width: u32,
    height: u32,
    ref_orbit_len: u32,  // actual escape iter of reference, <= max_iter
    escape_radius_sq: f32,
    param_0: f32,   // reserved
    param_1: f32,   // reserved
}

@group(0) @binding(0) var<uniform> params: PtParams;
@group(0) @binding(1) var<storage, read_write> output: array<u32>;
@group(0) @binding(2) var<storage, read> reference_orbit: array<vec2<f32>>;
```

Each PT kernel defines: `fn pt_iterate(dc: vec2<f32>) -> u32`
The common template computes `dc` via pixel_to_complex minus center (a delta, not absolute).

**Glitch handling on GPU:**
A two-pass approach is cleanest:
- Pass 1: each thread writes 0xFFFFFFFF to `output[i]` on glitch (or a dedicated glitch flag buffer)
- Pass 2 (CPU): re-render flagged pixels using CPU PT or direct f64

**Integration path:**
1. Add `RenderBackend::PerturbationGpu` variant (or `Perturbation` with a `use_gpu: bool` field)
2. Add `load_pt_shader()` and `compose_pt_shader()` to `wgpu_backend.rs`
3. New Rust upload function: `upload_reference_orbit(orbit: &[(f32, f32)]) -> wgpu::Buffer`
4. New GPU dispatch that binds the reference orbit buffer alongside the params and output buffers

**No changes needed to escape-time pipelines** — PT GPU is fully parallel infrastructure.

#### Precision Limitations: f32 Delta Range

GPU compute shaders operate in f32. This creates a hard precision ceiling for GPU PT.

At zoom Z with image width W pixels:
- Pixel offset dc ≈ 3.5 / (Z * W)
- At zoom=1e10, W=1920: dc ≈ 1.8e-13   (representable in f32, relative error ~1.2e-7 → abs error ~2e-20)
- At zoom=1e13, W=1920: dc ≈ 1.8e-16   (still representable in f32)
- At zoom=1e16, W=1920: dc ≈ 1.8e-19   (representable in f32 subnormal; precision degrades fast)
- At zoom=1e20, W=1920: dc ≈ 1.8e-23   (below f32 subnormal range — all dc become 0.0)

The f32 useful range for GPU PT is approximately **zoom 1e10 to 1e16-1e18**. Below 1e10,
direct GPU f64 (escape-time) is faster because it avoids the reference orbit overhead. Above
~1e18, the dc values underflow f32 and the GPU produces garbage (all pixels identical).

The reference orbit itself (truncated f64 → f32 for GPU) introduces an additional error of
roughly r_n * 1.2e-7 per step. This compounds through the delta recurrence. In practice this
limits quality at higher zoom even within the "representable dc" range.

**Practical conclusion:**
- Direct GPU (escape-time, f32): works up to zoom ~1e6 (starts showing aliasing beyond that)
- GPU PT (f32 delta): extends GPU usability to zoom ~1e13-1e16 (3-6 orders of magnitude gain)
- CPU PT (f64 delta): works up to zoom ~1e300 (limited only by BigFloat reference orbit)
- CPU HiPrec (BigFloat per pixel): works at any zoom but extremely slow

The dual pipeline naming convention adopted here:
- **"Perturbation"** = CPU PT (BigFloat reference orbit + f64 delta). This release.
- **"Perturbation GPU"** = CPU BigFloat reference orbit + GPU f32 delta. Future release.

Both modes share the same reference orbit computation. The GPU variant uploads the orbit
to VRAM and dispatches the delta loop on GPU. When the user is at zoom > ~1e16, the GUI
should warn that GPU PT precision is insufficient and suggest CPU PT instead.

**Target release for GPU PT:** v0.3.x (after the full GPU fractal rollout completes in
v0.2.9 and the pipeline family stabilizes). The capability table should gain a
"PT GPU f32" column at that point.

### Tetration GPU Implementation
Per v0.2.0's gradual GPU rollout strategy, this release adds GPU support for **Tetration** - the final fractal.

**Implementation:**
- [x] Create `tetration_kernel.wgsl` shader
- [x] Handle all 4 escape criteria modes (magnitude, real, imaginary, either)
- [x] Pass escape_mode as param_1, threshold as param_0
- [x] Added Tetration to GPU-capable fractal list in `wgpu_backend.rs` and `gpu_test.rs`
- [x] `complex_cpow` helper implemented; does not collide with `complex_pow` (scalar)

**Technical Challenge:**
Tetration uses `c^z` which requires complex exponentiation:
```
c^z = exp(z * ln(c))
    = exp((z_re + j*z_im) * (ln|c| + j*arg(c)))
```

This requires implementing complex logarithm and exponential in WGSL:
- [x] Implement `complex_ln(c)` helper (in tetration_kernel.wgsl)
- [x] Implement `complex_exp(z)` helper (in tetration_kernel.wgsl)
- [x] Implement `complex_cpow(base, exp)` — named `complex_cpow`, no collision

**CRITICAL naming collision:** `common.wgsl` defines:
```wgsl
fn complex_pow(z: vec2<f32>, power: f32) -> vec2<f32>   // scalar power
```
Tetration needs complex-to-complex exponentiation. Name it differently to avoid a silent
type mismatch or shadowing issue. Suggested: `complex_cpow(base: vec2<f32>, exp: vec2<f32>)`.

**Shader Pseudocode:**
```wgsl
fn complex_ln(z: vec2<f32>) -> vec2<f32> {
    let r = length(z);
    let theta = atan2(z.y, z.x);
    return vec2<f32>(log(r), theta);
}

fn complex_exp(z: vec2<f32>) -> vec2<f32> {
    let r = exp(z.x);
    return vec2<f32>(r * cos(z.y), r * sin(z.y));
}

fn complex_cpow(base: vec2<f32>, exp: vec2<f32>) -> vec2<f32> {
    return complex_exp(complex_mul(exp, complex_ln(base)));
}

fn check_escape(z: vec2<f32>, threshold: f32, mode: u32) -> bool {
    switch (mode) {
        case 0u: { return dot(z, z) > threshold * threshold; }  // Magnitude
        case 1u: { return abs(z.x) > threshold; }                // Real
        case 2u: { return abs(z.y) > threshold; }                // Imaginary
        case 3u: { return abs(z.x) > threshold || abs(z.y) > threshold; } // Either
        default: { return false; }
    }
}
```
