## Orbit Accumulation Rendering — Algorithm Specification

### What the algorithm does (plain English)

The chaos game renders the Julia set as a geometric object by tracing backward orbits.
Instead of asking "does this pixel escape?" (escape-time), it asks "how often does an
orbit land on this pixel?" (density). The Julia set emerges as the region where orbit
density is highest.

### Pseudocode

```
Given: N IFS maps  g_i(z) = sqrt(z - c_i),  each with probability p_i
       Image dimensions W x H
       Complex-plane viewport (center, zoom)
       Total orbit samples S  (e.g. 10,000,000)
       Discard count D (e.g. 50 — burn-in to reach the attractor)

1. Allocate density buffer: histogram[W][H] = 0   (u32 or u64 per pixel)
2. Pick starting point z = some arbitrary complex number (e.g. 0+0i)
3. For step = 0 .. S+D:
     a. Choose map index i with probability p_i
     b. Compute w = z - c_i
     c. Choose sign s = +1 or -1 randomly (each branch of sqrt)
     d. z = s * sqrt(w)
        - sqrt of complex number: sqrt(a+bi) = sqrt(r) * (cos(theta/2) + i*sin(theta/2))
          where r = |w|, theta = atan2(b, a)
     e. If step > D (past burn-in):
        - Map z to pixel coordinates (px, py)
        - If (px, py) is inside the image bounds:
            histogram[py][px] += 1

4. Normalize histogram to [0, max_iter-1] range:
     - Find max_count = max(histogram)
     - For each pixel: normalized[i] = (histogram[i] / max_count) * (max_iter - 1)
     - Optionally use log normalization: normalized[i] = log(1 + histogram[i]) / log(1 + max_count) * (max_iter - 1)

5. Return normalized[] as Vec<u32> — this feeds into the existing coloring pipeline
   exactly like escape-time iteration counts do.
```

### Why log normalization matters 

Raw density is extremely uneven — a few pixels near the Julia set boundary accumulate
thousands of hits while most get single digits. Without log scaling, the image is
essentially binary (black everywhere, bright at a few points). Log normalization
compresses the dynamic range so structure becomes visible. This is analogous to how
the Buddhabrot uses log density.

### How this integrates with the existing architecture

The key insight: **the output of orbit accumulation is a Vec<u32> of the same shape as
escape-time iteration counts**. Once normalized to [0, max_iter-1], it is indistinguishable
from escape-time data. The entire downstream coloring pipeline (colormaps, period modulation,
interior color, log scale, color offset) works unchanged.

The `Fractal` trait's `iterate(c_real, c_imag, params, max_iter) -> u32` signature is
per-pixel and cannot express orbit accumulation (which is a global operation across all
pixels). Therefore, orbit accumulation must be implemented as an **alternative compute
function** — a peer to `compute_iterations()`, not an override of `iterate()`.

### Architecture: where it fits

```
Current pipeline:
  compute_iterations()  -->  Vec<u32>  -->  apply_colors_from_cache()  -->  RGBA buffer
  compute_iterations_hiprec()  -->  Vec<u32>  ----^

New pipeline addition:
  compute_orbit_density()  -->  Vec<u32>  ----^
                                    |
                          (same coloring path, no changes needed)
```

The only change is adding a new compute function and wiring it into the dispatch points
that currently call `compute_iterations()`. No changes to:
- The `Fractal` trait
- `apply_colors_from_cache()`
- `color_from_iterations()` (scala_chromatica)
- Export pipeline (it gets a Vec<u8> RGBA buffer; doesn't care how it was made)
- Filtering / supersampling
- FractalIterations cache struct (stores Vec<u32>, works for density too)

## Architecture Decision: orbit_accumulation.rs as shared infrastructure

### Why a standalone module is the right choice

orbit_accumulation.rs is NOT a "Multi-Julia IFS helper file." It is a **general-purpose
density-rendering backend** — the orbit-accumulation counterpart to rendering.rs (which
is the escape-time rendering backend). Both produce `Vec<u32>` that feed the same
coloring pipeline.

The chaos game for IFS Julia sets and the Buddhabrot share the same infrastructure:

  1. A histogram buffer sized to the viewport (pixel-mapped from complex coords)
  2. An orbit generator (fractal-specific — each fractal runs its own orbit logic)
  3. A normalization pass (histogram -> [0, max_iter-1])
  4. Output as Vec<u32> compatible with apply_colors_from_cache()

What differs per fractal is only step 2 — how orbits are generated:

  | Fractal             | Orbit generation                                          |
  |---------------------|-----------------------------------------------------------|
  | Multi-Julia IFS     | z -> +/-sqrt(z - c_i), single long orbit, chaos game      |
  | Buddhabrot          | For each pixel c: run z->z^2+c, if it escapes, plot the   |
  |                     | entire orbit trajectory into the histogram                 |
  | Anti-Buddhabrot     | Same as Buddhabrot but plot non-escaping orbits            |
  | Nebulabrot          | Buddhabrot with 3 separate histograms (R/G/B channels)    |
  |                     | at different max_iter values                              |
  | General 2D IFS      | Affine-map chaos game (Sierpinski, Barnsley fern, etc.)   |

The module therefore exposes **reusable primitives** that all orbit-accumulating fractals
will use, while each fractal provides its own orbit-stepping closure or trait method:

```
orbit_accumulation.rs provides:
  DensityBuffer         — histogram[W*H] with complex-to-pixel mapping
    .increment(z, view) — maps complex z to pixel, bumps histogram if in-bounds
    .normalize(max_iter, use_log) -> Vec<u32>  — log or linear normalization
    .merge(&other)      — combine two buffers (for multithreading)
    .width(), .height()

orbit_accumulation.rs also provides:
  complex_sqrt(w) -> Complex64   — principal sqrt of complex number
  compute_orbit_density(view, fractal, params, max_iter) -> Vec<u32>
    — high-level dispatch: calls fractal.accumulate_orbits() then normalizes
```

Each orbit-accumulating fractal implements the orbit logic itself. The `Fractal` trait
gains one new method:

```rust
fn accumulate_orbits(&self, density: &mut DensityBuffer, view: &FractalView,
                     params: &HashMap<String, f64>) { ... }
```

Default implementation panics (like iterate_hiprec). Only called when
`uses_orbit_accumulation()` returns true. This keeps orbit generation fractal-specific
while all the buffer management, normalization, and pipeline integration is shared.

When the Buddhabrot is added in a future release, it implements `accumulate_orbits()` with
its own logic (iterate z^2+c for all starting points, plot escaping trajectories) and
reuses the same DensityBuffer and normalization. Zero orbit_accumulation.rs changes needed.

### Log normalization vs existing UI log scale — investigation note

- [ ] **CHECK**: The existing UI "Logarithmic Scale" checkbox applies `log10(t * 10.0)`
  in scala_chromatica's `color_from_iterations()` AFTER the iteration count is already
  normalized to `[0, 1]`. It compresses the colormap position nonlinearly.

  For orbit accumulation, the log normalization happens EARLIER — converting the raw
  density histogram (where values span many orders of magnitude, e.g. 1 to 100,000)
  into the `[0, max_iter-1]` integer range before it ever reaches the coloring pipeline:
  `normalized = log(1 + count) / log(1 + max_count) * (max_iter - 1)`

  These are two different operations at two different stages:
  - Density log-normalization: `raw_density -> Vec<u32>` (orbit_accumulation.rs)
  - Color log-scale: `u32 -> [0,1] -> log-compressed [0,1] -> color` (scala_chromatica)

  They can be combined (log-normalize density, THEN apply log color scale) for even more
  compression, or used independently. The density log-normalize is critical for getting
  any image at all; the color log-scale is an optional artistic tweak on top.

  **Decision**: Keep `use_log_density` as a separate density-stage parameter. Confirm
  during Phase 6 testing whether the UI log scale checkbox provides additional useful
  visual control on top of it or if it becomes redundant. If redundant in practice, note
  it but don't remove — it still applies to all other fractals.

### Phase 3: CPU multithreading

The orbit itself is sequential, but we can run **multiple independent orbits** in
parallel and merge their density buffers. This is embarrassingly parallel.

**Key design constraint**: Output must be **bit-identical regardless of thread count**.
The user controls one seed; changing thread count is a pure performance knob.

- [x] **3a.** `compute_orbit_density()` already implements K=64 parallel decomposition with rayon:
  - Accept `max_threads: usize` (0 = use rayon default)
  - **Fixed sub-orbit decomposition** (thread-count-independent):
    1. From the user's master `seed`, pre-generate K sub-orbit seeds where K is a
       fixed constant (K=64). This is trivially fast — 64 integer hashes, nanoseconds.
       `sub_seed[i] = hash(master_seed, i)` using a mixing function
       (e.g. `master_seed.wrapping_mul(0x9e3779b97f4a7c15).wrapping_add(i as u64)`)
    2. Each sub-orbit runs `total_samples / K` steps (remainder distributed to first
       sub-orbits: sub-orbit i gets `total_samples / K + (i < total_samples % K) as u64`)
    3. Hand all K jobs to `rayon::par_iter()` — rayon distributes across available
       threads via work-stealing. Whether there are 2 or 16 threads, the K=64 jobs
       and their seeds are identical.
    4. Each job creates its own DensityBuffer and calls `fractal.accumulate_orbits()`
    5. Merge all K density buffers via `density.merge()`
    6. Normalize the merged buffer once
  - `max_threads` limits rayon pool size (same pattern as existing CPU rendering) but
    does NOT change the sub-orbit count or seeds
  - The Fractal trait requires `Sync` already so `&dyn Fractal` can be shared

  **Reproducibility guarantee**:
  - Same master seed = same K sub-orbit seeds = same K sub-orbits = same merged
    density = **bit-identical output regardless of thread count**
  - The user controls one number. Thread count is invisible to the output.
  - K=64 is large enough for good load-balancing across any reasonable thread count
    and small enough that 64 DensityBuffer allocations are negligible overhead

- [x] **3b.** The high-level `compute_orbit_density()` is the parallel version
  with `max_threads` from the render config.

### Phase 6: Hi-Precision pipeline (orbit accumulation)

### Phase 6.5: GPU orbit accumulation for Multi-Julia IFS

GPU orbit accumulation is architecturally different from the per-pixel escape-time
shaders. The existing GPU pipeline dispatches one thread per pixel and writes one
iteration count. Orbit accumulation dispatches one thread per **sub-orbit** and
writes to many pixels via atomic increments on a shared density histogram.

**WGSL constraint**: `atomic<u64>` is not available. Use `atomic<u32>` which caps
per-pixel counts at ~4 billion — sufficient for orbit accumulation (even 50M samples
spread across a 1920x1080 image average ~24 hits/pixel; hotspots reach thousands,
never billions).

**Architecture: orbit_common.wgsl (new composition template)**

A new shader template parallel to `common.wgsl`:
- Bindings:
  - `@binding(0)` uniform: `OrbitParams` struct (center, zoom, width, height,
    samples_per_thread, burn_in, seed_base, num_maps, map data packed as f32 arrays)
  - `@binding(1)` storage `read_write`: `array<atomic<u32>>` density histogram (W*H)
- Entry point: `@compute @workgroup_size(64) fn main()` — 1D dispatch, each invocation
  runs one sub-orbit of `samples_per_thread` steps
- Per-fractal kernel: `fn trace_orbit(seed: u32, samples: u32, burn_in: u32)` — replaces
  `iterate_fractal` from the escape-time pattern. Calls `atomicAdd(&density[idx], 1u)`
  for each post-burn-in step.
- `// {{ORBIT_KERNEL}}` marker for composition, same pattern as `// {{FRACTAL_KERNEL}}`

**Dispatch model:**
- Total sub-orbits K=64 (match CPU), dispatched as `dispatch_workgroups(K, 1, 1)`
  with `@workgroup_size(64)` means 1 workgroup of 64 threads = 64 sub-orbits
- Each thread gets a deterministic seed derived from `seed_base + global_invocation_id.x`
- After dispatch completes, read back the `atomic<u32>` buffer to CPU, normalize on CPU
  (reuse existing normalization logic), then color as usual

**Implementation steps:**

  - `OrbitParams` uniform struct (matches a new Rust struct `GpuOrbitParams`)
  - `array<atomic<u32>>` density storage buffer
  - `pixel_to_index(z) -> u32` coordinate mapping (inverse of `pixel_to_complex`)
  - `orbit_xorshift(state: ptr<function, u32>) -> u32` — PRNG in WGSL
  - `complex_sqrt_wgsl(w: vec2<f32>) -> vec2<f32>` — f32 complex sqrt

## RESOLVED BUG: OOM at Supersampled Export (was BLOCKING Phase 7a)

### Error
```
[EXPORT-PERF] Target: 3840x2160, Render: 15360x8640 (4x SS)
memory allocation of 1061683200 bytes failed
(exit code: 0xc0000409, STATUS_STACK_BUFFER_OVERRUN)
```

### Root cause
Orbit accumulation uses `DensityBuffer` (Vec<u64>, one u64 per pixel). The rayon
fold/reduce pattern keeps one DensityBuffer per active thread as an accumulator.

At 15360x8640 (4x supersample of 3840x2160):
- One DensityBuffer = 132,710,400 pixels x 8 bytes = **1,061,683,200 bytes (~1,012 MB)**
- The crashed allocation (1,061,683,200 bytes) is EXACTLY one DensityBuffer
- System: 32 GB RAM, 20 logical CPUs (rayon default = 20 threads)
- Peak memory with fold/reduce: 20 buffers x 1,012 MB = ~20 GB + RGBA (~506 MB) + Vec<u32> (~506 MB) = ~21 GB
- OS and application overhead push this past available memory

### CONSTRAINT: DO NOT skip supersampling
The user wants Gaussian downsampling for noise reduction. This is a valid use case
for stochastic orbit accumulation (reduces visual noise in the density histogram).
Supersample + Gaussian downsample must work. Any solution that skips or disables
supersampling for orbit accumulation is REJECTED.

### Previous wrong fix (reverted)
Tried setting supersample=1 for orbit accumulation in export.rs. Reverted. Do not
re-attempt this approach.

### Solution candidates (must implement one)

**A: Tile-based accumulation** — Process image in tiles. Each tile gets its own
   small DensityBuffer. Downside: each orbit step can land anywhere, so full orbit
   must run per tile. Cost = N_tiles x orbit_steps. Memory-bounded but slow.

**B: Thread-count capping** — Limit rayon threads based on available memory.
   E.g., if buffer > 500 MB, cap to floor(available_RAM / buffer_size) - headroom.
   Simple but fragile, varies by system.

**C: u32 DensityBuffer for large exports** — Use u32 per pixel instead of u64.
   Halves buffer to ~506 MB each. 20 threads x 506 MB = ~10 GB. Fits in 32 GB.
   Risk: u32 overflow at ~4B. Scaled samples ~80M over K=64 sub-orbits = ~1.25M
   steps per sub-orbit. Hotspot overflow unlikely but possible in extreme cases.

**D: Atomic shared buffer (RECOMMENDED)** — ONE DensityBuffer with AtomicU64 (or
   AtomicU32) per pixel. All threads write to same buffer via atomic increment.
   Peak memory: 1 buffer (~1 GB) + RGBA (~0.5 GB) + Vec<u32> (~0.5 GB) = ~2 GB.
   Well within 32 GB regardless of thread count. Atomic ops are ~2-5x slower than
   plain writes but orbit accumulation is PRNG+sqrt-bound, not memory-write-bound.
   Use Relaxed ordering since all reads happen after writes complete.
   Implementation: new AtomicDensityBuffer type alongside existing DensityBuffer,
   used when resolution exceeds a threshold (e.g. > 100M pixels or > 500 MB buffer).

**E: Two-pass upscale** — Accumulate at target res, upsample density, color at SS res,
   downsample. Mathematically questionable for stochastic data. Probably worse than
   direct Gaussian blur on the final image. Not recommended.
