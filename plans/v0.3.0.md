# Plan v0.3.0 - Job Queue Foundation

**Fractal**: TBD - to be determined before release finalization

## Overview
Version 0.3.0 introduces a background job queue system for rendering. This enables non-blocking exports and batch operations while the user continues exploring in the GUI.

Preview-process parity is intentionally deferred. v0.3.0 scopes the worker/IPC foundation for queued renders first; live preview subprocess management should be scheduled in a later release rather than left implicit here.

## Dependencies
- **v0.2.7** - GPU acceleration complete (job queue should use GPU where available)
- **v0.1.7** - CLI/JSON settings (job queue uses same format)
- Library architecture from v0.2.3

## Job Queue Architecture

### Core Concept
The job queue runs as a **separate process** spawned from the GUI. This provides:
- True parallelism (not blocked by GUI thread)
- Crash isolation (job failure doesn't crash GUI)
- Resource management (can limit CPU/GPU usage independently)
- Persistence (queue survives GUI restart)

### Components

#### 1. Job Definition
```rust
pub struct RenderJob {
    pub id: Uuid,
    pub settings: FractalSettings,  // JSON-serializable, same as CLI
    pub output_path: PathBuf,
    pub priority: JobPriority,
    pub status: JobStatus,
    pub created_at: DateTime<Utc>,
    pub started_at: Option<DateTime<Utc>>,
    pub completed_at: Option<DateTime<Utc>>,
    pub error: Option<String>,
}

pub enum JobPriority { Low, Normal, High }
pub enum JobStatus { Queued, Running, Completed, Failed, Cancelled }
```

### Resource Management

The job queue needs to respect system resources:

#### CPU Cores
- [ ] Add setting: "Worker CPU cores" (1 to max-1)
- [ ] Default: 50% of available cores (leave headroom for GUI/OS)
- [ ] Pass to rayon via `RAYON_NUM_THREADS` environment variable

#### GPU Utilization
- [ ] Add setting: "Use GPU for queued jobs" (yes/no/auto)
- [ ] If GUI is actively rendering preview, queue may need to wait
- [ ] Consider GPU memory limits for very large exports

#### Memory
- [ ] Estimate memory usage before starting job
- [ ] Warn if estimated usage exceeds available RAM
- [ ] Consider tiled rendering for very large exports

#### Phase 2: Enhanced Worker (v0.3.0)
- [ ] Progress reporting from worker to GUI

Note: v0.3.0 owns the worker/process foundation and the IPC for queued-job progress/cancel.
Foreground preview/manual-render cancellation should reuse this machinery in a later
rendering-focused release rather than introducing a second cancellation protocol.
