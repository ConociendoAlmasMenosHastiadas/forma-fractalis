# Plan v0.3.6 - Auto Rendering Mode

**Fractal**: TBD - to be determined before release finalization

Candidate fractal reference: https://paulbourke.net/fractals/symmetryinchaos/ (modified version; see the counterpart notes in `v0.2.5`)

## Overview
Version 0.3.6 introduces "Auto" as a first-class rendering backend option. By this point
the project has a full family of rendering pipelines: GPU (f32), CPU f64, Hi-Prec BigFloat,
and Perturbation Theory. Auto selects the most capable appropriate backend for the current
fractal and zoom level -- but it is never silent. Every selection decision is visible to the
user, every unsupported case is an explicit refusal, and the user can always override.

## Dependencies
- **v0.2.7** - Perturbation Theory pipeline (Mandelbrot power=2 only; this plan schedules the next explicit PT expansion)
- **v0.2.8+** - Full GPU coverage across all fractals
- **v0.2.x hi-prec series** - Hi-Prec BigFloat coverage across most/all fractals
- **v0.3.0** - Worker subprocess / progress IPC foundation, reused for cancellable long-running renders
- **v0.3.5** - Coordinate transforms, stable architecture before adding mode logic

## Perturbation Expansion Phasing

PT support beyond Mandelbrot must stay explicit and per-fractal. Auto mode depends on that
scope being formalized rather than implied.

- [ ] Extend PT support from Mandelbrot to Julia as the first post-v0.2.7 perturbation expansion
- [ ] Keep capability-table/runtime capability metadata explicit about which fractals support PT and which still require Hi-Prec fallback
- [ ] Do not imply universal PT support for higher-power or non-quadratic fractals until dedicated delta recurrences and parity coverage exist
- [ ] Revisit `Sinh Julia` PT only after the generalized post-Mandelbrot PT architecture is proven; it was explicitly deferred out of `v0.2.8` because the current PT path supports only Mandelbrot power = 2

## Design Principles

These are non-negotiable constraints on the Auto implementation:

1. **Auto is never silent.** The GUI must always display which backend is currently active
   and, when Auto selected it, a one-line reason why.
2. **No silent fallback.** If the preferred pipeline is unavailable and no acceptable
   alternative exists, Auto refuses to render and shows a clear error. It does not quietly
   downgrade to a less-accurate backend without telling the user.
3. **User override always wins.** Manual backend selection bypasses all Auto logic entirely.
   The manual selection is sticky across zoom changes.
4. **Precision loss is an error, not a warning.** If Auto determines that no supported
   pipeline can render the current view correctly, the render is blocked with a message
   explaining exactly why and what the user's options are.

## Backend Priority Order

Auto evaluates backends in this order for each render request:

```
GPU (f32)
  -> available? fractal has GPU shader? zoom within f32 precision range?
     YES -> use GPU, annotate "Auto: GPU (f32)"

CPU f64
  -> zoom within f64 precision range (~1e13 depending on canvas size)?
     YES -> use CPU f64, annotate "Auto: CPU (f64)"

Perturbation Theory
  -> fractal supports PT? (Mandelbrot power=2, Julia initially; see v0.2.7 scope)
     YES -> use PT, annotate "Auto: Perturbation Theory (BigFloat reference orbit)"

Hi-Prec BigFloat
  -> fractal supports hi-prec?
     YES -> use Hi-Prec, annotate "Auto: Hi-Prec BigFloat"
             Note: this is slow; no attempt is made to hide that from the user.
             Show estimated render time if above a threshold.

No pipeline available
  -> REFUSE. Display:
     "Auto mode cannot find a pipeline that can render [FractalName] at this zoom level
      accurately. Supported pipelines for this fractal: [list]. The current zoom requires
      precision beyond what those pipelines provide. Zoom out or switch to a fractal with
      Perturbation Theory support."
```

## Precision Threshold Computation

The f64 precision cutoff is not a magic constant. It depends on zoom level and canvas size:

```rust
/// Returns true if f64 arithmetic can represent pixel-level coordinates accurately.
/// Formula: pixel spacing = 3.5 / (zoom * canvas_width)
/// f64 has ~15.9 significant decimal digits. Cutoff when pixel_spacing < 1e-15.
fn f64_is_sufficient(zoom: f64, canvas_width: u32) -> bool {
    let pixel_spacing = 3.5 / (zoom * canvas_width as f64);
    pixel_spacing > 1e-14  // conservative margin: fail a decade before true floor
}
```

This function should be in a shared location (e.g. `number_utils.rs`) so the GUI status
display and the pipeline selector both use the same definition.

Similarly, a separate function should determine whether GPU f32 precision is sufficient:

```rust
/// f32 has ~7.2 significant digits. Cutoff is much earlier than f64.
fn f32_is_sufficient(zoom: f64, canvas_width: u32) -> bool {
    let pixel_spacing = 3.5 / (zoom * canvas_width as f64);
    pixel_spacing > 1e-6  // conservative
}
```

## GUI Changes

### Backend selector
The existing manual selector (CPU / GPU / Hi-Prec / PT) gains a new first option: **Auto**.
- Auto is the default for new installs (change the default in `RenderBackend` enum)
- Position: first in the list, visually separated from manual options (e.g. a divider)

### Active backend status line
Below the backend selector, always show a single line:

  Active: [backend name] | [reason if Auto]

Examples:
- `Active: GPU (f32)`  (manual selection — no reason shown)
- `Active: Auto -> GPU (f32) | fractal + zoom within f32 range`
- `Active: Auto -> CPU (f64) | GPU f32 precision insufficient at this zoom`
- `Active: Auto -> Perturbation Theory | f64 precision insufficient (zoom ~1e15)`
- `Active: Auto -> Hi-Prec BigFloat (slow) | PT not supported for this fractal`
- `Active: Auto -> BLOCKED | no pipeline supports Tetration at zoom 1e20`

The status line must update immediately whenever zoom, fractal type, or backend selection
changes. It is not a log; it always reflects the current state.

### Long-running render controls
This release is a reasonable place to expose cancellation/progress for manual renders because
Auto can legitimately choose very slow PT or Hi-Prec backends. The implementation must build
on the subprocess/IPC work from v0.3.0 rather than blocking the GUI thread again.

- [ ] Reuse the v0.3.0 worker/process IPC for long-running foreground renders instead of inventing a separate cancel/progress path
- [ ] Show percentage progress for active long-running renders when the backend can report row/tile/pixel completion
- [ ] Add a Cancel button for the currently running foreground render; cancelling keeps the last successfully rendered frame on screen
- [ ] Distinguish `Cancelled` from `Blocked` in the status presentation so a user can tell the difference between an explicit stop and a precision/support refusal
- [ ] Ensure PT and Hi-Prec progress callbacks are coarse enough that reporting overhead does not dominate the render itself

### Blocked render state
When Auto (or any pipeline) is blocked due to precision/support constraints:
- The preview panel shows the last successfully rendered frame (do not clear it)
- The status line turns red: `Active: Auto -> BLOCKED | [reason]`
- No render is attempted, no partial/corrupt output is shown
- An export triggered in this state is also blocked with the same message

## Backend Capability Registry

To drive Auto selection cleanly, formalize what each fractal supports. This is already
partially tracked in `plans/capability_table.md`. By v0.3.6, the table should be complete
and the application should read fractal capabilities at runtime rather than scattering
`if fractal_name == "..."` checks through the pipeline selector.

- [ ] Add a `capabilities()` method to the `Fractal` trait (or a parallel `FractalCapabilities`
  struct) returning which backends are supported
- [ ] Implement `capabilities()` for every fractal

## Backend Selection Heuristics (carried over from v0.2.5)

During v0.2.5 GPU profiling work, the following heuristics were deferred to this release.
They are prerequisites for a correct Auto implementation.

### Fractal-specific thresholds
Some fractals are faster on CPU at low iteration counts because GPU dispatch overhead
dominates. A simple per-fractal min-iteration threshold should gate the GPU path:
- Mandelbrot/BurningShip: GPU always wins at typical preview resolution
- MultiJuliaIFS (orbit accumulation): GPU wins for large canvases; CPU may win at < 256x256
- Tetration/Lemon (no GPU shader): always CPU

### Preview vs export size thresholds
The existing tiled render path already handles oversized exports. The heuristic needed here
is the opposite: at very small preview sizes (e.g. thumbnail), GPU dispatch overhead exceeds
actual compute time and CPU is faster. Suggested threshold: width * height < 128*128 → prefer CPU.

### Real-world benchmark data
Update `BENCHMARKS.md` with GPU vs CPU comparisons for each GPU-capable fractal at
1080p preview before implementing heuristics, so the thresholds are data-driven.
- [ ] Auto mode's pipeline selector reads from `capabilities()` exclusively —
  no hardcoded fractal-name checks

## Notes

- GPU f32 precision cutoff (~1e6) means Auto will switch to CPU f64 relatively quickly
  when zooming in. This transition should be tested and documented in the status line.
  A user who sees "Auto switched to CPU f64" should understand why without digging through docs.
- Hi-Prec BigFloat as the Auto fallback of last resort is intentionally slow. The status
  line should say "(slow)" when this backend is active so the user is not confused by
  the render taking minutes instead of seconds.
- The Perturbation Theory scope at v0.2.7 is limited to Mandelbrot power=2.
  Auto should reflect that exact starting point, then expand only as later plans land
  explicit per-fractal PT support (Julia first, then any further fractals with dedicated
  recurrences and validation).
